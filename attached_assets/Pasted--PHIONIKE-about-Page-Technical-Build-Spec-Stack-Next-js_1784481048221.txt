# PHIONIKE — /about Page Technical Build Spec
Stack: Next.js 14 (App Router) · Tailwind CSS · Framer Motion · Lucide React
Companion doc to `phionike-technical-spec.md` (Home), `phionike-services-technical-spec.md`
(Services), and `phionike-work-technical-spec.md` (Work). Shared tokens,
data-layer pattern, and rendering strategy are not repeated in full here.

---

## 0. Cross-Page Architecture Fix (applies retroactively to Home/Services/Work)

**Navbar active-state is currently hardcoded.** All prior specs describe the
"Home" link as the one with the active indicator. That was only ever correct
on the Home page. Fix: `Navbar` takes an `activePage` prop
(`'home' | 'about' | 'work' | 'services' | 'process-ai'`), and the active-
indicator underline renders on whichever link matches. Update the Home,
Services, and Work implementations to pass this prop rather than hardcoding
"Home" as active — this was a gap in every prior spec, not just this one.

## 3. Meet the Team — Bento Grid (corrected — this is the section to get exact)

Eyebrow: "The Team" (terracotta). Heading: "The people behind the products
you love." A supporting group photo (people sitting on steps) sits to the
right of this intro block, treated as a standalone editorial image, not part
of the grid below.

### This is not a uniform 4-column card grid — and it's not true CSS masonry either

v1 specifies one repeating card component (`aspect-[3/4.2]`, bio-vs-hover-
name binary state). The reference shows a genuinely mixed-content **bento
grid**: different tile types, different sizes, some tiles with no team
content at all. Naming this "masonry" (as commonly meant — CSS multi-column
auto-flow producing uniform-width, variable-height single-content-type
columns, the same technique used for the Portfolio grid on Home/Services/
Work) is the wrong implementation target. What's needed is a CSS Grid with
**explicit per-tile column/row spans**, mixing multiple distinct tile types:

**Tile types observed in the reference:**
1. `photoOnly` — a headshot, no caption at all.
2. `bioText` — flat color background, no photo, name + role + full bio paragraph.
3. `photoCaption` — headshot with a dark gradient overlay + name/role caption at the base.
4. `nameOnly` — flat color background, name + role only, no bio, no photo.
5. `decorativeFill` — flat color block, zero content. Pure visual rhythm/spacing.
6. `decorativeBar` — a thin, full-row-width rounded color bar, zero content — a rhythm break between rows, not a card at all.

**Sizing:** tiles vary — some `col-span-1 row-span-2` (tall), some
`col-span-2 row-span-1` (wide bars), most `col-span-1 row-span-1` (square).
Base grid: `grid grid-cols-2 md:grid-cols-4 auto-rows-[180px] gap-6`, each
tile's exact span set explicitly per its data entry (see schema below) — not
derived from content length or computed automatically.

### The randomization problem (this is the part worth being careful about)

If this needs to grow with a real, API-driven team roster later — and per
the site's established JSON-now/API-later pattern, it should — you can't
hand-place 12 fixed grid positions in JSX; that breaks the first time
headcount changes. But generating the tile-type/size assignment with
`Math.random()` inside the component at render time will cause a **Next.js
hydration mismatch**: the server renders one random arrangement during SSR,
the client re-renders a different random arrangement on hydration, producing
either a visible layout flash or a hydration error in the console.

**Fix: resolve the arrangement once, at data-authoring time, and store the
result as plain fields on each record — never compute it inside the
component.** Each team member's JSON entry carries its own `tileType` and
`gridSpan` already decided. Decorative filler/bar tiles are separate entries
in the same array (not tied to a person), interspersed by whoever authors
the content. If/when this becomes a real CMS-backed roster, the CMS entry
schema should include these same fields (perhaps with a sensible default
`tileType`/`gridSpan` computed **server-side at content-ingestion time**, not
client-side at render time) — same principle, different point in the pipeline.

```ts
type TeamTile =
  | {
      kind: 'member';
      id: string;
      name: string;
      role: string;
      bio?: string;              // present for bioText and photoOnly-with-hover-reveal tiles
      photoSrc?: string;
      tileType: 'photoOnly' | 'bioText' | 'photoCaption' | 'nameOnly';
      gridSpan: { col: 1 | 2; row: 1 | 2 };
      bgColor?: 'cobalt' | 'terracotta' | 'lavender' | 'mustard'; // for non-photo tiles
    }
  | {
      kind: 'decorativeFill' | 'decorativeBar';
      id: string;
      gridSpan: { col: 1 | 2; row: 1 | 2 };
      bgColor: 'cobalt' | 'terracotta' | 'lavender' | 'mustard';
    };
```

**Per-type interaction behavior:**
- `photoOnly` — static, no hover state (matches reference: several photo
  tiles show no caption at all, hover or not).
- `bioText` / `nameOnly` — static, content is always visible, no hover mechanic.
- `photoCaption` — static caption always visible over the gradient overlay;
  optionally, a `group-hover:` micro-interaction (subtle scale on the photo,
  `group-hover:scale-105`) for polish, but no curtain/reveal mechanic is
  actually needed here since the caption isn't hidden by default.
- `decorativeFill` / `decorativeBar` — no interaction, `aria-hidden="true"`
  (these carry no information, shouldn't be announced to screen readers or
  receive focus).

This replaces v1's single "bio-shown vs. hover-reveal-curtain" binary
entirely — the reference doesn't show evidence of a hidden-then-revealed
bio anywhere; every tile's content (or lack of it) appears to be static.

**Content-QA flag (same bug pattern as the Work page's testimonials):** every
visible name in the capture reads "Marcus Thorne, UI/UX Designer" —
repeated across all 8 team tiles — while the bio paragraph beneath still
refers to "Roopam" in the first person. This is the same name/bio mismatch
already flagged on the Work page's reviews section, which suggests it's a
**systemic issue in this project's dummy content generation**, not a one-off.
Recommend a single content-QA pass across the whole site's placeholder data
before real copy goes in, rather than fixing it independently per page. The
JSON fixture below uses distinct, internally-consistent placeholder names
rather than repeating "Marcus Thorne" eight times, since shipping a visibly
repeated name obviously isn't the intent.

**Mixed: bg-color for text/filler/bar tiles, bg-image required for every
photo tile (photoOnly and photoCaption types).**

## 4. Life at Phionike (corrected — alternating bands, not a 2×2 grid)

v1 specifies "a symmetrical 2x2 grid matrix." The reference is **four
full-width alternating photo/text bands**, zig-zagging left/right, not a
grid at all:

- Eyebrow (missing from v1): "Our Culture"
- A full-width establishing photo (bright studio space) sits above the first
  band — also missing from v1.
- Band 1 — "We Learn Together": photo left, text block right (`bg-terracotta`).
- Band 2 — "We Build Together": text block left (`bg-lavender`), photo right.
- Band 3 — "We Grow Together": photo left, text block right (`bg-cobalt`).
- Band 4 — "We Care Deeply": text block left (`bg-mustard`), photo right.

Each band: `grid grid-cols-1 md:grid-cols-2`, photo `aspect-[4/3] md:aspect-auto
h-full object-cover`, text block padded generously (`p-10 md:p-16`) with
heading + paragraph. Alternate `md:order-2` on the photo per band to achieve
the zig-zag, rather than building 4 different layout variants.

**Text-contrast rule, consistent with the Services page correction:** mustard
and lavender are light backgrounds — use dark charcoal text on those two
bands. Cobalt and terracotta are saturated enough for white text.

**bg-image required** for the establishing shot and all 4 band photos.

## 7. Mobile / Responsive — Open Item

No mobile capture provided yet. The bento team grid is the piece most likely
to need a real rebuild rather than a reflow — a hand-varied-span grid
doesn't collapse gracefully to a single column by just changing `grid-cols`.
Reasonable default until a capture arrives: collapse every tile to
`col-span-1 row-span-1` on mobile (uniform single-column stack, spans
ignored below `md:`), which is safe but is explicitly a placeholder, not a
confirmed design. Flag for the same reason as prior pages' open mobile items
— don't let this quietly become "final."

## 8. Rendering & Performance

- Server Components by default. Nothing on this page needs `useState`/
  `useScroll` — the team grid's hover micro-interactions are pure
  `group-hover:` CSS, no client JS required.
- All photo tiles (mosaic, team, culture bands): `next/image`, lazy, never
  `priority` — consistent with every other page.
- Since the bento arrangement is pre-resolved data (§3), rendering the team
  grid is a trivial `.map()` — no client-side layout computation at all.
